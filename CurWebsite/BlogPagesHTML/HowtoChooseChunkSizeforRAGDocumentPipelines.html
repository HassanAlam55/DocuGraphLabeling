How to Choose Chunk Size for RAG Document Pipelines

Chunk size is the single highest-leverage decision in a RAG pipeline. Get it right and your retrieval is precise, your context windows are efficient, and your generated answers are accurate. Get it wrong and the system retrieves irrelevant passages, wastes tokens on context that dilutes the answer, and generates responses that are either too vague (chunks too large) or missing critical context (chunks too small).

The problem is that most chunking advice treats documents as flat text. "Use 512 tokens with 10% overlap" works as a starting default, but it ignores the reality that documents have structure: headers, paragraphs, tables, lists, figures, and footers that define where meaningful boundaries exist. Splitting a table across two chunks destroys the data. Splitting a paragraph mid-sentence fragments the meaning. Merging a header with an unrelated paragraph from the next section creates a chunk that confuses retrieval.

This guide covers the chunk size decision from first principles: what tradeoffs chunk size controls, how document structure should inform those decisions, what sizes work for which document types, how to handle the elements that naive chunking breaks, and how to evaluate whether your chunk size is actually working.

The Two Failure Modes Chunk Size Controls

Every chunk size is a tradeoff between two failure modes. Understanding both is the starting point for choosing well.

Chunks too small: lost context

When chunks are too small (under 100 tokens), each chunk contains a fragment of an idea rather than a complete thought. The embedding captures the fragment accurately, and retrieval finds the right fragment, but the generated answer lacks the surrounding context needed to produce a useful response.

Example: A legal contract states "The termination clause requires 90 days written notice, except in cases of material breach, where immediate termination is permitted." At 50-token chunks, this gets split into two fragments: "The termination clause requires 90 days written notice" and "except in cases of material breach, where immediate termination is permitted." A query about termination notice periods retrieves the first fragment and misses the exception. The generated answer is factually incomplete.

Chunks too large: diluted relevance

When chunks are too large (over 2,000 tokens), each chunk contains multiple topics, ideas, or document sections. The embedding becomes a blurred average of everything in the chunk. Retrieval matches the chunk because part of it is relevant, but most of the content is noise that dilutes the answer.

Example: A 2,000-token chunk from a financial report contains the company overview, the revenue summary, and the start of the risk factors section. A query about revenue figures retrieves this chunk because it contains revenue data, but the company overview and risk factor fragments waste context window space and may confuse the generator into producing an answer that mixes revenue figures with risk language.

The goal is to find the chunk size where each chunk contains enough context to be self-explanatory but not so much that it mixes unrelated content.

Starting Defaults That Actually Work

Before optimizing, you need a baseline. These defaults come from the FloTorch 2026 benchmark (which tested chunking strategies across 50 academic papers) and consistent findings across production RAG systems.

General-purpose retrieval: 512 tokens, 50 to 100 token overlap. This is the default that works acceptably on most document types. The FloTorch benchmark measured 69% end-to-end accuracy with recursive character splitting at 512 tokens, the highest of any single strategy tested.

Factoid queries (short, specific answers): 256 to 512 tokens. Smaller chunks increase retrieval precision because the embedding more tightly represents the specific fact rather than the surrounding context.

Analytical queries (multi-paragraph reasoning): 512 to 1,024 tokens. Larger chunks provide the surrounding context that analytical answers require. A query like "What are the implications of the Fed rate decision for tech sector valuations?" needs chunks large enough to capture the reasoning, not just the data points.

Conversational or FAQ-style content: 128 to 256 tokens. Each question-answer pair is a natural chunk. Larger chunks merge multiple Q&A pairs, reducing retrieval precision.

Never exceed 2,500 tokens per chunk. Research consistently shows that generation quality degrades beyond this threshold. The generator's attention becomes too diffuse across the large context, producing answers that are less focused and less accurate than answers generated from smaller, more targeted chunks.

Why Document Structure Should Drive Chunking

The defaults above treat all text equally. In reality, documents have structure that tells you exactly where meaningful boundaries exist, if you have access to that structure.

A PDF document is not a flat string of text. It is a hierarchy of elements: page headers that repeat on every page, section headings that introduce topics, paragraphs that develop ideas, tables that present structured data, lists that enumerate items, figures that illustrate concepts, and footers that provide reference information.

Each element type has a natural chunk boundary. A section heading signals the start of a new topic. A table is a self-contained data unit. A list is a complete enumeration. A figure caption explains a visual.

Document layout analysis identifies these elements and their boundaries. When you know that a document region labeled "section_header" appears at position Y, you know that a topic boundary exists at that position. Chunking at topic boundaries produces chunks that are semantically coherent rather than arbitrarily split.

This is the connection that most chunking guides miss: labeled document structure eliminates the need for expensive semantic chunking algorithms. If you already have layout labels that tell you where every header, paragraph, table, and figure starts and ends, you do not need to compute embeddings on overlapping windows to find semantic boundaries. The labels give you the boundaries directly.

AI Asset Management's DocuGraph platform produces exactly this structural metadata: bounding boxes and element classifications for every region on every page, exported as structured JSON. This output tells a chunking pipeline that lines 1 through 3 are a page_header, lines 4 through 22 are a paragraph, lines 23 through 45 are a table, and lines 46 through 48 are a caption. The chunking logic uses these boundaries instead of sliding a fixed-size window across raw text.

Structure-Aware Chunking: The Rules

When you have document structure labels (from layout analysis, from markdown headers, or from HTML tags), apply these rules to produce chunks that respect the document's natural organization.

Rule 1: Never split a table across chunks

Tables are the single most common element that naive chunking destroys. A table split across two chunks produces two fragments that each contain partial rows, partial columns, or headers separated from their data. Neither fragment is useful for retrieval or generation.

If a table fits within your maximum chunk size, the entire table is one chunk (or part of a larger chunk that includes the preceding context that introduces the table). If a table exceeds your maximum chunk size, each row (or group of rows) becomes a chunk, with the table headers prepended to every chunk so each fragment retains its column context.

For detailed guidance on extracting and handling tables from PDFs, the table detection step is a prerequisite for correct chunking.

Rule 2: Keep headings with their content

A section heading separated from the content it introduces is useless. A chunk that starts with a heading and contains the following content is self-explanatory.

When chunking at heading boundaries, include the heading as the first element of the chunk that contains the section's content, not as the last element of the previous chunk. If a section is long enough to require multiple chunks, prepend the section heading to each chunk so every chunk has the heading context.

Rule 3: Treat lists as atomic units

A list (bulleted, numbered, or definition list) is a single logical unit. Splitting a list at an arbitrary point produces a fragment that starts mid-enumeration, which confuses both retrieval (the embedding misses the list's topic, which is usually in the sentence before the list) and generation (the answer references items without the list context).

If the list plus its introductory sentence fits within the maximum chunk size, keep it as one chunk. If it exceeds the limit, split at list-item boundaries (never mid-item) and prepend the introductory sentence to each split.

Rule 4: Attach captions to their elements

A figure caption separated from its figure reference produces an orphaned caption that retrieval may match but that provides no useful context without the figure. Similarly, a table caption separated from the table it describes loses the connection between the description and the data.

When chunking, always include captions in the same chunk as the element they describe. If the element (figure or table) is too large for a single chunk, include the caption in every split.

Rule 5: Strip repeated elements

Page headers, page footers, and page numbers that repeat on every page add noise to chunks without adding information. A chunk that starts with "Acme Corporation Confidential" and ends with "Page 14 of 97" on every page wastes tokens on repeated metadata.

Strip repeated headers and footers before chunking. Preserve them as document-level metadata that attaches to every chunk from that document (for filtering and source attribution) but not as content within the chunk text.

Chunk Size by Document Type

Different document types have different natural chunk sizes because their structural units vary in length. A research paper's natural unit (a section) is longer than an invoice's natural unit (a line item).

Invoices and receipts: 128 to 256 tokens

Invoices contain many short, independent data elements: vendor name, invoice number, line items, subtotals, tax amounts, totals, payment terms, dates. Each element is a potential retrieval target. Small chunks ensure that a query about the invoice total retrieves the total, not the total buried inside a 500-token chunk that also contains the vendor address and payment terms.

Contracts and legal documents: 512 to 1,024 tokens

Legal clauses are the natural chunking unit for contracts. Each clause (termination, indemnification, confidentiality, governing law) is a self-contained legal concept that ranges from 200 to 800 tokens. Chunking at clause boundaries produces semantically coherent chunks. Avoid splitting mid-clause because legal language depends on qualifiers and exceptions that span the full clause.

Research papers and academic articles: 512 to 1,024 tokens

Research papers have clear structural sections (abstract, introduction, methods, results, discussion). Each section is too long for a single chunk, but subsections and paragraphs within each section provide natural boundaries. Chunk at paragraph boundaries within sections, prepending the section heading to each chunk.

Financial reports: 256 to 512 tokens

Financial reports mix narrative text (management discussion, risk factors) with tabular data (income statements, balance sheets). The narrative sections chunk well at 512 tokens. The tabular sections should be chunked by table, with each table as a separate chunk regardless of its token count relative to the narrative chunk size.

Medical records and clinical notes: 256 to 512 tokens

Clinical notes contain discrete observations, diagnoses, medications, and treatment plans that are each independent retrieval targets. Small chunks ensure that a query about a specific medication retrieves the medication note, not the medication note buried inside a 1,000-token chunk that also contains the patient history.

Government forms and regulatory filings: 256 to 512 tokens

Government forms have labeled fields that are natural chunk boundaries. Each field (applicant name, address, filing status, declaration) is a discrete unit. Chunk by field or field group rather than by token count.

Technical documentation and manuals: 512 to 1,024 tokens

Technical docs have hierarchical heading structures that provide natural boundaries. Chunk at the lowest heading level (h3 or h4) and prepend the parent headings (h1 and h2) to each chunk for context.

The Overlap Decision

Overlap is the number of tokens shared between adjacent chunks. It exists to prevent information loss at chunk boundaries: if a key sentence spans the boundary between chunk N and chunk N+1, overlap ensures that sentence appears in both chunks so it can be retrieved from either one.

How much overlap

10 to 20% of chunk size is the production standard. For 512-token chunks, use 50 to 100 tokens of overlap. This range captures boundary sentences without significantly increasing the total number of chunks (and therefore the index size and retrieval cost).

More than 20% overlap creates diminishing returns. The index grows, retrieval cost increases, and the marginal value of each additional overlap token decreases. At 50% overlap, you have nearly twice as many chunks as 0% overlap, but retrieval precision does not double.

Zero overlap is acceptable when chunking at structural boundaries. If every chunk starts at a heading and ends at the next heading, there are no arbitrary boundaries where information might be lost. Structure-aware chunking reduces or eliminates the need for overlap.

When overlap matters most

Overlap matters most when using fixed-size chunking (where boundaries are arbitrary) and least when using structure-aware chunking (where boundaries are meaningful). If your preprocessing step produces document structure labels that define where elements start and end, you can reduce or eliminate overlap because the boundaries are not arbitrary.

The Metadata Layer Most Teams Skip

A chunk without metadata is a chunk you cannot filter, trace, or debug. Every chunk in a production RAG pipeline should carry metadata that answers: where did this chunk come from?

Essential metadata per chunk

Source document identifier. File name, document ID, or URL. Required for source attribution in generated answers.

Page number. Which page of the source document this chunk appears on. Required for verification (the user can check page 14 to confirm the answer).

Section heading. The heading under which this chunk appears. Enables retrieval filtering ("search only in the Methods section") and provides context for the generator.

Element type. Is this chunk a paragraph, a table, a list, a heading-plus-content block? Element type enables type-specific retrieval (search only tables, skip headers and footers).

Chunk index. The position of this chunk within the document. Enables sequential retrieval ("get the next chunk after this one") for queries that need more context than a single chunk provides.

Attaching element type metadata requires knowing what type of element each chunk contains. This is where document AI preprocessing adds value: the element classifications from layout analysis become the metadata fields on each chunk.

The Preprocessing Step Before Chunking

Most chunking guides start with "take your text and split it." But the quality of the text you start with determines the quality of the chunks you produce. For PDF documents, several preprocessing steps must happen before chunking begins.

OCR for scanned documents

If the PDF contains only image data (no embedded text layer), OCR must extract the text before any chunking can happen. OCR accuracy directly affects chunk quality: a misrecognized word becomes a permanent error in every chunk that contains it.

Layout analysis for structure detection

Semantic segmentation and layout detection identify the structural elements on each page: headers, paragraphs, tables, figures, lists, footers. This structural metadata is what enables structure-aware chunking.

Without layout analysis, the chunking pipeline receives raw text with no indication of where structural boundaries exist. With layout analysis, the pipeline receives text annotated with element types and boundaries that inform every chunking decision.

Table extraction

Tables require dedicated extraction that preserves row-column relationships. Raw text extraction from tables (reading left to right, top to bottom across cells) destroys the tabular structure. Dedicated table extraction preserves cell associations so the chunked table retains its meaning.

Repeated element removal

Headers, footers, and page numbers that repeat on every page should be stripped before chunking and preserved as document-level metadata. If they are not stripped, they appear in chunks and pollute the embedding with non-informative repeated text.

How to Evaluate Your Chunk Size

Choosing a chunk size is a hypothesis. Evaluating it is the experiment. Without evaluation, you are guessing.

Retrieval precision

For a set of test queries, measure what percentage of retrieved chunks are actually relevant to the query. High precision means the chunk size is producing embeddings that accurately represent chunk content. Low precision means chunks contain mixed topics and the embeddings are too diffuse.

How to measure: Create 50 to 100 test queries with known relevant passages. For each query, retrieve the top 5 chunks and manually label each as relevant or not relevant. Precision = relevant chunks / total retrieved chunks.

Context relevance

For each retrieved chunk, measure what percentage of the chunk's content is relevant to the query. High context relevance means the chunk is tightly focused. Low context relevance means the chunk contains relevant content mixed with irrelevant content that wastes context window space.

How to measure: For each relevant retrieved chunk, highlight the sentences that actually answer the query. Count the relevant tokens versus total tokens. Context relevance = relevant tokens / total tokens in chunk.

Answer faithfulness

Does the generated answer accurately reflect the content of the retrieved chunks? Hallucinations and inaccuracies indicate that the generator is struggling with the context, which may mean chunks are too large (diluted context), too small (missing context), or mixing unrelated content.

How to measure: For each test query, generate an answer and compare it against the source chunks. Flag any claim in the answer that is not supported by the retrieved chunks.

The evaluation loop

Run the evaluation at your current chunk size. Identify the failure mode (low precision suggests chunks too large, missing context suggests chunks too small, mixed relevance suggests wrong boundaries). Adjust the chunk size. Re-evaluate. Repeat until the metrics stabilize.

Most teams need 3 to 5 evaluation cycles to converge on a chunk size that works for their specific documents and queries.

Advanced Strategies Worth Knowing

Parent-child chunking

Embed small child chunks (128 to 256 tokens) for retrieval precision, but return the larger parent chunk (512 to 1,024 tokens) or the full parent section for generation context. This decouples retrieval granularity from generation context size, solving the precision-versus-context tradeoff.

Contextual chunk headers

Prepend a 50 to 100 token context summary to each chunk before embedding. The summary includes the document title, the section heading, and a one-sentence description of the chunk's content. This technique, used in Anthropic's Contextual Retrieval approach, improves retrieval accuracy by giving each chunk's embedding awareness of its broader context.

Late chunking

Embed the full document through a long-context embedding model first, then split the embeddings into chunk-sized segments. Each chunk's embedding carries context from the entire document because the attention computation happened before the split. This approach, demonstrated by Jina AI, improved retrieval by 6.5 nDCG points over traditional chunk-then-embed approaches.

Adaptive chunk sizing

Use different chunk sizes for different sections of the same document based on content density. Dense, fact-heavy sections (financial data, specification tables) get smaller chunks. Narrative sections (discussion, analysis) get larger chunks. This requires knowing the content type of each section, which again depends on document structure labels from layout analysis or heading detection.

Summary

Chunk size is a tradeoff between precision (smaller chunks) and context (larger chunks). The starting default of 512 tokens with 10 to 20% overlap works for most general-purpose RAG pipelines, but the right chunk size depends on your document type, your query type, and the structure of your documents.

The highest-leverage improvement is moving from fixed-size chunking (which ignores document structure) to structure-aware chunking (which splits at headings, keeps tables intact, preserves lists as units, and attaches captions to their elements). This requires document preprocessing that identifies element types and boundaries, but the retrieval quality improvement is substantial.

Chunk size is a hypothesis, not a configuration. Evaluate it with test queries, measure retrieval precision and context relevance, identify the failure mode, adjust, and re-evaluate. Most teams converge in 3 to 5 cycles.
