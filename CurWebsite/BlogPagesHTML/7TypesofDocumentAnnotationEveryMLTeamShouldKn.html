7 Types of Document Annotation Every ML Team Should Know

Most ML teams know how to annotate images and text. Bounding boxes, sentiment labels, named entities in a paragraph - that part is well understood. But when the data lives inside documents - PDFs, scanned forms, contracts, financial reports, insurance claims - the annotation work changes completely.

Documents are not flat text. They are structured, visual, and relational all at once. A table in a financial report is not just text - it has rows, columns, headers, and cell relationships that only make sense when you preserve the layout. A contract is not just paragraphs - it has parties, dates, and clauses that reference each other across pages. An invoice has fields and values that belong together as pairs, not as isolated tokens.

This means document annotation requires its own set of techniques, separate from general text or image annotation. And if your ML team is building anything in the document AI space - extraction models, classification systems, RAG pipelines, compliance automation - knowing these seven types is not optional. It is the foundation.

Here are the seven types of document annotation that matter most, ordered from structural to semantic, from simple to complex.

1. Document Layout Annotation

Layout annotation is the starting point for every document AI pipeline. It answers the most basic structural question: what is each region of this page, and where does it sit?

In layout annotation, you segment a document page into distinct regions and label each one with its structural role. A page might be divided into a title, section headers, body paragraphs, tables, figures, footnotes, page headers, and page footers. Each region gets a bounding box (its x/y coordinates on the page) and a category label.

This is the annotation type that trains models like LayoutLM (Microsoft Research), DiT (Document Image Transformer), and Donut. Without accurate layout annotations, none of these models can learn where document elements begin and end, which means every downstream task - extraction, classification, search - starts with bad inputs.

The standard public datasets for layout annotation use flat taxonomies with 5 to 11 labels. PubLayNet (IBM Research) uses five: Text, Title, List, Table, and Figure across 360,000+ scientific article pages. DocLayNet (also IBM) uses eleven labels across 80,000+ pages from financial reports, legal documents, patents, and government filings. For a deeper look at how to pick the right label set for your use case, see our guide on choosing a document labeling taxonomy.

When you need it: Any time you are building a document understanding model, a PDF parser, or a retrieval system that needs to chunk documents into meaningful sections rather than arbitrary text blocks.

What the annotation looks like: A bounding box around each region of the page, tagged with labels like "Title," "Section-header," "Text," "Table," "Figure," "Footnote," "Page-header," and "Page-footer."

Common pitfall: Using a taxonomy that is too coarse. If you label everything as "Text" versus "Table" and nothing else, your model cannot distinguish a section header from a footnote - and that distinction matters enormously for retrieval quality and extraction accuracy.

2. Named Entity Recognition (NER) Annotation

NER annotation moves from structure to meaning. Instead of labeling what a region is (header, paragraph, table), you label what specific entities appear within the text and what type each entity is.

In a legal contract, NER annotation identifies every party name, effective date, jurisdiction, governing law reference, and monetary amount. In a bank statement, it tags account numbers, transaction dates, payee names, and balances. In a medical discharge summary, it marks patient identifiers, diagnosis codes, medication names, and provider names.

Document NER is harder than standard text NER because position matters. The same string "March 15, 2026" might be a contract effective date in one location and a filing date in another. Document NER models need both the text and the spatial context (where the entity sits on the page relative to labels and headers) to classify correctly. This is why multi-modal models like LayoutLMv3 and LILT, which combine text embeddings with layout coordinates, consistently outperform text-only NER models on document tasks.

When you need it: Any extraction task where you need to pull specific pieces of information from documents - names, dates, amounts, IDs, codes, terms - and classify each one by type.

What the annotation looks like: Text spans highlighted and tagged with entity types. For example, "Acme Corporation" tagged as ORG, "January 1, 2026" tagged as EFFECTIVE_DATE, "$2,500,000" tagged as MONETARY_AMOUNT.

Common pitfall: Annotating entities without spatial context. If you strip the text out of the PDF and annotate it as plain text, you lose the positional information that document NER models depend on. Always annotate on the original document layout, not on extracted text.

3. Key-Value Pair Extraction Annotation

Key-value annotation is one of the highest-demand document annotation types in enterprise ML, and it is also one of the most misunderstood.

A key-value pair is a field name linked to its corresponding value in a document. On an invoice, "Invoice Number" is the key and "INV-2024-0831" is the value. On a KYC form, "Full Legal Name" is the key and "Sarah Chen" is the value. On a tax return, "Adjusted Gross Income" is the key and "$142,300" is the value.

The annotation task is not just identifying each key and each value separately (that would be NER). It is explicitly linking each key to its corresponding value as a pair. This linkage is what makes key-value annotation different from entity recognition, and it is what allows extraction models to understand that "$142,300" belongs to "Adjusted Gross Income" rather than to "Total Deductions" two lines below.

This annotation type powers the document processing automation that banks, insurance companies, accounting firms, and government agencies depend on. Every time an invoice gets processed without a human typing the amount into a system, or a loan application gets routed based on automatically extracted fields, there is a key-value extraction model behind it - and that model was trained on key-value annotated documents. For the technical details of how this works with PDFs specifically, see our guide on PDF data extraction methods.

When you need it: Form processing, invoice automation, claims intake, loan underwriting, regulatory filing extraction - any workflow where structured field-value pairs need to come out of semi-structured documents.

What the annotation looks like: Each key highlighted and linked to its value with a directional association. "Vendor Name" → "Acme Corp." "Invoice Date" → "08/15/2026." "Line Total" → "$4,250.00."

Common pitfall: Treating keys and values as independent entities instead of linked pairs. A model trained on key-value pairs learns the association pattern (the key is usually to the left of or above the value, with specific visual proximity). A model trained on isolated entities does not learn that association and will mismap values to the wrong keys when layouts vary.

4. Table Structure Annotation

Tables are everywhere in business documents - financial statements, audit reports, insurance schedules, regulatory filings, lab results, pricing sheets - and they are notoriously difficult for ML models to handle correctly.

Table structure annotation goes deeper than layout annotation. Where layout annotation labels an entire table region as "Table," table structure annotation labels the internal components: header rows, data rows, column headers, row headers, merged cells, sub-headers, total rows, and footnotes within the table.

This internal structure is what extraction models need to understand that the number "4,231" in a specific cell belongs to the column "Q3 Revenue" and the row "North America Division." Without table structure annotation, the model sees the table as a blob of text with no relational meaning.

Table structure annotation is particularly challenging because table layouts vary wildly. A financial statement might use nested headers, spanning cells, and hierarchical row groupings that look completely different from a simple two-column price list. Multi-page tables that split across page breaks add another layer of complexity. For ML teams working on this problem, see our technical deep-dive on extracting tables from PDFs with machine learning.

When you need it: Financial document processing, regulatory compliance reporting, scientific data extraction, any workflow where tabular data inside PDFs needs to be converted into structured, queryable formats.

What the annotation looks like: Bounding boxes around each cell, row, and column, with labels distinguishing "Table Header," "Column Header," "Row Header," "Data Cell," "Merged Cell," "Total Row," and "Table Caption."

Common pitfall: Annotating only cell boundaries without labeling the header-to-data relationships. A model that knows where cells are but does not know which row is the header will extract numbers without context - and numbers without context are useless for downstream analytics.

5. Document Classification Annotation

Document classification is the simplest type of document annotation conceptually, but it plays a critical role in large-scale document processing systems.

In classification annotation, you assign a single label (or sometimes multiple labels) to an entire document or page. The label represents the document type: invoice, contract, purchase order, medical record, tax return, insurance claim, research paper, correspondence.

This sounds basic, and it is. But when an organization receives 50,000 incoming documents per month through email, fax, and upload portals, the first step in every processing pipeline is routing each document to the correct workflow. An invoice goes to accounts payable. A contract goes to legal review. A claim goes to the adjuster queue. Misclassification means the document enters the wrong pipeline, which causes delays, errors, and compliance failures.

Classification annotation is also used for page-level labeling within multi-page documents. A mortgage loan package might contain 200 pages spanning multiple document types: the application, income verification, credit report, appraisal, title search, and closing disclosure. Page-level classification annotation teaches the model to segment the package into its component documents automatically.

When you need it: Document routing, mailroom automation, document set segmentation, compliance sorting, and any intake workflow that processes mixed document types at volume.

What the annotation looks like: A single label per document or per page. "invoice," "contract," "purchase_order," "medical_record," "tax_return," "insurance_claim."

Common pitfall: Training on clean, single-type documents and then deploying on messy, real-world inputs. Production documents often arrive as multi-page scans with cover letters, sticky notes, and unrelated pages mixed in. Your training data needs to reflect that messiness, not just the ideal case.

6. Relation and Entity Linking Annotation

Relation annotation connects the entities within a document to each other, transforming flat entity lists into structured, meaningful relationships.

This is where document annotation moves beyond "what is in this document" to "how do the things in this document relate to each other." After NER identifies "Acme Corp" as an organization and "$5 million" as a monetary amount, relation annotation labels the link between them - specifying that "$5 million" is the "acquisition_price" paid by "Acme Corp." After NER identifies "Section 4.2" and "indemnification," relation annotation connects them - specifying that "Section 4.2" contains an "indemnification_clause."

Entity linking goes a step further by connecting entities within a document to entries in an external knowledge base or standardized reference. A medication name in a clinical document gets linked to its entry in the RxNorm database. A company name in a financial filing gets linked to its SEC CIK number. A legal citation gets linked to the specific statute or case it references.

Relation annotation is essential for building models that need to answer questions about documents rather than just extract isolated facts. A question like "What is the indemnification cap in the Acme Corp agreement?" requires the model to understand the relationship between the company, the clause type, and the monetary amount - not just to find each piece independently.

When you need it: Contract analysis, compliance checking, medical records processing, financial filing analysis, and any application where the relationships between entities carry as much meaning as the entities themselves.

What the annotation looks like: Directed arrows between entity annotations, with relationship type labels. "Acme Corp" -[party_to]→ "Service Agreement." "$5M" -[indemnification_cap_of]→ "Service Agreement." "Section 4.2" -[contains]→ "Non-compete Clause."

Common pitfall: Defining too many relationship types. Start with 5 to 10 high-value relationship types that directly support your downstream task. Annotators cannot maintain consistency across 30+ relation types, and your model will struggle with sparse training data for rare types.


7. Knowledge Graph Annotation

Knowledge graph annotation is the most advanced type of document annotation, and it is the one most ML teams skip - usually because they do not realize it exists as a distinct annotation task, or because they think it requires an entirely separate pipeline.

Knowledge graph annotation combines all of the previous types - layout, NER, key-value extraction, table structure, classification, and relation extraction - into a unified, interconnected representation. The result is not a set of isolated labels or extracted fields. It is a structured graph where every entity, section, and relationship is linked, queryable, and traceable back to its source location in the original document.

Think of it this way: NER tells you "this document mentions Acme Corp and $5 million." Relation annotation tells you "Acme Corp paid $5 million." Knowledge graph annotation connects that to the contract section where it appears, the date it was signed, the law that governs it, the other party involved, and the specific clause that defines the payment terms - creating a web of linked information that spans the entire document and can extend across multiple documents.

This is not just a nice-to-have for research teams. Knowledge graph annotation is becoming the standard for enterprise document AI, especially for organizations deploying Retrieval-Augmented Generation (RAG) systems where LLMs need to ground their answers in source documents. The quality of document annotation directly determines retrieval quality, and retrieval quality determines whether the LLM generates accurate, traceable answers or hallucinated ones.

Doing each step manually with separate tools introduces compounding errors at each handoff.

How These 7 Types Build on Each Other

These annotation types are not independent choices. They form a progression, and most real-world document AI systems use several of them together.

Layout annotation is always the foundation. You cannot extract entities from a document if you do not know where the text regions, tables, and headers are. Every document AI pipeline starts here.

NER and key-value extraction sit on top of layout annotation. Once you know the structure of the page, you can identify and classify the entities and field-value pairs within each structural region.

Table structure annotation is a specialized extension of layout annotation for the specific challenge of tabular data - which is common enough and complex enough to require its own annotation approach.

Document classification can run independently (it only needs the full document, not its internal structure), but it becomes more accurate when combined with layout features. A model that sees "this document has a table with columns labeled Debit, Credit, and Balance" can classify it as a bank statement more reliably than one that only reads the text.

Relation annotation and knowledge graph annotation require all of the lower levels to be in place. You need entities (from NER), structure (from layout), and field-value associations (from key-value extraction) before you can annotate the relationships between them.

Quality Metrics That Matter for Document Annotation

Not all annotation is created equal. Here is how to measure whether your document annotations are actually good enough to train reliable models.

Inter-Annotator Agreement (IAA) is the foundation metric. Have two or more annotators independently annotate the same documents, then measure how often they agree. For layout annotation, a Cohen's Kappa above 0.8 is excellent. For NER and relation annotation, 0.7 or higher is the generally accepted minimum. If your IAA is below 0.6, your annotation guidelines need revision before you annotate anything else.

Bounding Box IoU (Intersection over Union) measures the spatial accuracy of layout and table annotations. An IoU above 0.75 for layout regions and above 0.8 for table cells indicates that annotators are drawing boxes consistently enough for model training.

Entity-Level F1 Score measures NER annotation quality by comparing annotated entities against a gold standard. Compute precision (how many annotated entities are correct), recall (how many true entities were found), and F1 (the harmonic mean). Target F1 above 0.85 for production NER training data.

Relation-Level F1 applies the same precision/recall/F1 framework to relation annotations. This metric is typically lower than entity-level F1 because relations are harder to annotate consistently. An F1 above 0.75 for relation annotation is considered strong.

Confidence Scoring is critical for automated annotation workflows. Every auto-generated label should carry a confidence score, with high-confidence labels accepted automatically and low-confidence labels routed for human review. This is the mechanism that makes human-in-the-loop annotation efficient at scale.

FAQ: Document Annotation for ML Teams

What are the main types of document annotation? The seven main types are: (1) document layout annotation, (2) named entity recognition annotation, (3) key-value pair extraction annotation, (4) table structure annotation, (5) document classification annotation, (6) relation and entity linking annotation, and (7) knowledge graph annotation. Each serves a different purpose in the document AI pipeline, from structural segmentation to semantic relationship mapping.

Which type of document annotation should I start with? Start with layout annotation. It is the foundation that every other annotation type depends on. Once your model can reliably segment pages into headers, paragraphs, tables, and figures, you can add NER, key-value extraction, and the other types incrementally.

What is the difference between document annotation and text annotation? Text annotation works with plain text strings. Document annotation works with documents that have visual layout, spatial positioning, tables, images, and multi-page structure. Document annotation preserves and labels this structural information, which text annotation ignores.

How many annotated documents do I need to train a model? For layout analysis using transfer learning from pre-trained models like LayoutLMv3, 500 to 2,000 well-annotated pages are often sufficient for strong performance. For NER and key-value extraction on a specific document type, 200 to 1,000 documents with consistent annotations typically produce usable models. More data always helps, but annotation quality matters more than volume.

Can document annotation be automated? Yes. What is knowledge graph annotation for documents? Knowledge graph annotation connects all entities, sections, and relationships within a document (and across documents) into a structured, queryable graph. It goes beyond extracting isolated facts to mapping how those facts relate to each other. This is the annotation type that powers RAG pipelines, enterprise search, and contract intelligence systems.

How does document annotation quality affect RAG systems? Directly and significantly. RAG systems retrieve document passages to ground LLM responses. If documents are poorly segmented, if entities are missed, or if relationships are unmapped, the retrieval system pulls irrelevant or incomplete context. The LLM then generates hallucinated or inaccurate answers. High-quality document annotation is the single biggest lever for improving RAG accuracy.
