Top 10 Public Datasets for Training Document AI Models

Building a document AI model without good training data is like building a house without a foundation. The model architecture matters, the hyperparameters matter, but the training data determines whether the final result holds up under real-world conditions.

Fortunately, the document AI community has produced several high-quality public datasets that you can use to train layout analysis models, information extraction systems, document classifiers, and visual question answering pipelines without starting from scratch.

This guide covers the ten most important public datasets for document AI training, organized by what they help you build. For each dataset, we cover what it contains, what tasks it supports, what models it pairs well with, and where it falls short so you can choose the right dataset for your specific project.

Layout Analysis Datasets

These datasets provide labeled document pages where every region has been annotated with bounding boxes and element classifications. They are the foundation for training models that understand document structure.

1. PubLayNet

What it is: The largest document layout analysis dataset, containing over 360,000 document page images with annotations for five element types: text, title, list, table, and figure.

Who created it: IBM Research, using an automated matching process that aligned the XML representations of scientific articles from PubMed Central with their corresponding PDF renderings.

Why it matters: PubLayNet's sheer scale makes it the default pre-training dataset for layout detection models. Most publicly available pre-trained checkpoints for Faster R-CNN, Mask R-CNN, and DocLayout-YOLO were initially trained on PubLayNet. When you download a pre-trained layout detection model from a research repository, there is a strong chance it was trained on this dataset.

Best for: Pre-training general layout detection models. The large volume gives models a robust baseline understanding of document structure before fine-tuning on domain-specific data.

Limitations: All documents are scientific articles from PubMed Central. The layouts are predominantly single-column or two-column academic paper formats. Models trained exclusively on PubLayNet perform well on similar scientific documents but show significant accuracy drops on invoices, legal contracts, government forms, and other document types with different structural conventions.

The five-category taxonomy (text, title, list, table, figure) is also quite coarse. It does not distinguish between page headers and section headers, does not include captions or footers, and groups all non-title text into a single "text" category. For applications that need finer-grained element classification, PubLayNet's taxonomy may be insufficient.

Access: Available on GitHub under a CDLA-Permissive license.

2. DocBank

What it is: A large-scale document layout dataset containing 500,000 pages from arXiv scientific papers with 12 fine-grained token-level categories.

Who created it: Microsoft Research, using a weak supervision approach that aligned LaTeX source files with their rendered PDF output to generate annotations automatically.

Why it matters: DocBank's 12-category taxonomy is significantly more granular than PubLayNet's 5 categories. It distinguishes between abstract, author, caption, date, equation, figure, footer, list, paragraph, reference, section, table, and title. This granularity lets models learn to distinguish between element types that PubLayNet merges together.

The token-level annotation is also distinctive. Instead of drawing bounding boxes around regions, DocBank assigns a label to every text token (word) on the page. This format is particularly well-suited for training multi-modal models like LayoutLM that process text tokens with positional information.

Best for: Training models that need fine-grained text classification and token-level understanding. Particularly useful for LayoutLM fine-tuning where token-level labels are required.

Limitations: Like PubLayNet, all documents are academic papers (from arXiv rather than PubMed Central). The layout diversity is limited to academic formatting conventions. The automated annotation process using LaTeX source alignment can introduce noise, particularly for elements where the LaTeX structure does not cleanly map to the visual layout.

Access: Available on GitHub under a permissive license.

3. DocLayNet

What it is: A manually annotated dataset containing 80,863 pages from diverse document sources, including financial reports, government documents, scientific papers, patents, laws and regulations, and technical manuals. It uses 11 element categories.

Who created it: IBM Research, with human annotators who manually drew bounding boxes and assigned labels to every element on each page.

Why it matters: DocLayNet is the most layout-diverse document dataset available. Unlike PubLayNet and DocBank, which are limited to academic papers, DocLayNet includes documents from six distinct categories with fundamentally different visual structures. This diversity makes it the best available dataset for evaluating how well a layout model generalizes across document types.

The 11-category taxonomy includes caption, footnote, formula, list-item, page-footer, page-header, picture, section-header, table, text, and title. This provides the most practical label set of the three major layout datasets, with distinctions (page-header vs. section-header, footnote as a separate category) that directly map to real-world document processing needs.

Research using DocLayNet demonstrated that models trained on narrow document distributions (academic papers only) show 12 to 18 percentage point accuracy drops when tested on other document types. This finding has been influential in shifting the community's focus from dataset size to dataset diversity.

Best for: Training and evaluating layout models that need to work across multiple document types. The go-to evaluation benchmark when you need to assess real-world generalization rather than academic-paper-specific performance.

Limitations: At 80,863 pages, DocLayNet is significantly smaller than PubLayNet (360K+) and DocBank (500K). The smaller size means it may not provide enough examples for some element categories. Financial documents and government forms, while included, are still underrepresented compared to what a production system would encounter.

Access: Available on GitHub under a CDLA-Permissive license.

Choosing between the three layout datasets

If you are building a layout detection model, here is the practical guidance:

Use PubLayNet for pre-training when you need a large volume of layout examples to give your model a general understanding of document structure. Use DocBank when you are training a token-level model like LayoutLM and need fine-grained text classification. Use DocLayNet for evaluation and for fine-tuning when your production documents span multiple types.

For most real-world projects, the best approach is pre-training on PubLayNet's large corpus, then fine-tuning on DocLayNet's diverse pages, and finally fine-tuning again on your own domain-specific labeled data. This three-stage training pipeline consistently produces the strongest production models.

If your project involves specialized document types (invoices, legal contracts, medical records, government forms) that none of these datasets adequately represent, you will need to create additional labeled training data from your own documents to close the distribution gap.

Information Extraction Datasets

These datasets provide documents annotated with specific entity labels for training models that pull structured data from document content.

4. FUNSD (Form Understanding in Noisy Scanned Documents)

What it is: A small but influential dataset containing 199 real, noisy scanned form documents with annotations for 9,707 semantic entities across 31,485 words.

Who created it: Guillaume Jaume and colleagues at the Universite Catholique de Louvain.

Why it matters: FUNSD is the standard benchmark for form understanding, the task of identifying and classifying key entities (questions, answers, headers, and other elements) within form documents. Nearly every document AI paper that reports results on form understanding includes FUNSD scores.

The dataset also includes entity linking annotations that map which "answer" entities correspond to which "question" entities, enabling training for relationship extraction tasks. This linking information is what makes FUNSD unique among small document datasets.

Best for: Benchmarking form understanding models. Fine-tuning NER models for form field extraction. Evaluating entity linking (question-answer pairing) in document contexts.

Limitations: The dataset is very small (199 documents, with only 149 for training). It is useful for fine-tuning pre-trained models and for benchmarking, but it is not large enough to train a model from scratch. The four entity types (question, answer, header, other) reflect form structure rather than semantic content, which limits its usefulness for extraction tasks that need domain-specific entity types.

Access: Available on Zenodo under a free research license.

5. CORD (Consolidated Receipt Dataset)

What it is: A receipt dataset containing 1,000 receipt documents with 30 unique key entity labels organized into four super-categories: menu, total, sub-total, and void.

Who created it: Researchers at NAVER CLOVA AI (Park et al., 2019).

Why it matters: CORD provides one of the richest entity label sets of any document AI dataset. With 30 entity types covering menu item names, prices, counts, sub-totals, total amounts, tax, tips, payment methods, and more, it enables training models that understand receipt content at a granular level.

The dataset is commonly used alongside Donut (also from NAVER), which was designed specifically for end-to-end document parsing without OCR. CORD provides the benchmark data for evaluating Donut's receipt parsing capabilities.

Best for: Training and evaluating receipt parsing models. Benchmarking end-to-end document understanding models like Donut. Learning how fine-grained entity taxonomies are structured for a specific document type.

Limitations: Only 1,000 documents, all receipts. The formatting conventions of receipts (narrow, single-column, vertically stacked) are structurally different from most other business documents. Models fine-tuned on CORD learn receipt-specific patterns that do not transfer well to invoices, contracts, or forms.

Access: Available through the NAVER CLOVA AI GitHub repository.

6. SROIE (Scanned Receipts OCR and Information Extraction)

What it is: A dataset of 1,000 scanned restaurant receipt images annotated for OCR and key information extraction with four entity types: company, date, address, and total.

Who created it: Presented at the ICDAR 2019 competition by Huang et al.

Why it matters: SROIE has been a standard benchmark since 2019 for evaluating the full pipeline from raw scanned image to extracted structured data. The competition format (with a public leaderboard) drove significant progress in document extraction accuracy, and most document AI models report SROIE scores as part of their evaluation.

The four entity types are simple but highly practical: every receipt processing application needs to extract the company name, date, address, and total. SROIE measures how well models handle this core extraction task on real scanned images with varying quality.

Best for: Benchmarking end-to-end OCR-to-extraction pipelines. Evaluating how models handle real scanned document quality (noise, rotation, varying resolution). Comparing extraction accuracy across the full document processing stack.

Limitations: Only four entity types, limiting its usefulness for training models that need to extract a wider range of fields. All documents are restaurant receipts, so the format diversity is minimal.

Access: Available through the ICDAR 2019 competition page.

Document Classification Datasets

7. RVL-CDIP (Ryerson Vision Lab Complex Document Information Processing)

What it is: A large-scale document image classification dataset containing 400,000 grayscale document images labeled with 16 document type categories.

Who created it: Adam Harley and colleagues at Ryerson University, sourced from the larger IIT-CDIP collection of tobacco industry documents.

Why it matters: RVL-CDIP is the standard benchmark for document image classification, the task of determining what type of document a page represents. The 16 categories include letter, form, email, handwritten, advertisement, scientific report, scientific publication, specification, file folder, news article, budget, invoice, presentation, questionnaire, resume, and memo.

At 400,000 images (320,000 training, 40,000 validation, 40,000 test), it is large enough to train classification models from scratch. The dataset has driven progress in document classification accuracy from 89% (BERT using text only) to 95%+ (multi-modal models using text and image together).

Best for: Training and benchmarking document type classifiers. Evaluating whether a model can sort incoming documents into categories before applying type-specific extraction. Pre-training visual document models before fine-tuning for other tasks.

Limitations: All documents are tobacco industry records from the 1990s and earlier, which means the visual styles, fonts, and formatting conventions are dated. Modern documents (digital-native PDFs with contemporary typography) look different from these scanned legacy documents. The 16 categories are broad and may not match the classification needs of specific business applications.

Access: Available through the RVL-CDIP project page.

Visual Question Answering Datasets

8. DocVQA (Document Visual Question Answering)

What it is: A dataset containing over 50,000 question-answer pairs on approximately 12,000 document images, designed for training models that can answer natural language questions about document content.

Who created it: Mathew et al. at the Computer Vision Center (CVC), Barcelona.

Why it matters: DocVQA introduced the task of visual question answering for documents, where a model receives a document image and a natural language question ("What is the total amount?") and must produce the correct answer by reading and understanding the document. This task tests the full stack of document understanding: OCR, layout comprehension, and semantic reasoning.

DocVQA is the primary benchmark for evaluating models like LayoutLMv3, Donut, and Pix2Struct on their ability to understand and reason about document content, not just classify or extract predefined fields. The evaluation metric (Average Normalized Levenshtein Similarity, or ANLS) measures how close the model's answer text is to the ground truth.

Best for: Training and evaluating document QA models. Benchmarking vision-language models for document understanding. Building systems where users can ask natural language questions about uploaded documents.

Limitations: The documents are primarily business letters, invoices, and forms from the IIT-CDIP collection. The questions are generated by human annotators and may not represent the types of questions real users ask in production applications. Models that perform well on DocVQA do not automatically perform well on domain-specific QA tasks.

Access: Available on the DocVQA website and HuggingFace Datasets.

Multilingual Datasets

9. XFUND (Multilingual Form Understanding)

What it is: A multilingual form understanding dataset containing documents in 7 languages: Chinese, Japanese, Spanish, French, Italian, German, and Portuguese. Each language includes forms with key-value pair annotations.

Who created it: Microsoft Research, as an extension of FUNSD to multilingual settings. Released alongside the LayoutXLM model.

Why it matters: XFUND is the only major document AI dataset that covers non-English languages at scale. Most document AI research is conducted exclusively on English documents, which means models trained on other datasets have limited multilingual capability. XFUND fills this gap by providing annotated forms in seven languages with consistent annotation conventions.

The dataset was designed to evaluate cross-lingual transfer: can a model trained on English forms perform well on Chinese or Japanese forms? Research using XFUND showed that multi-modal models (using text, layout, and image together) transfer across languages significantly better than text-only models because layout patterns are more language-independent than textual patterns.

Best for: Training and evaluating multilingual document understanding models. Testing cross-lingual transfer from English to other languages. Building form processing systems for international organizations that handle documents in multiple languages.

Limitations: Only 7 languages are covered, all using either Latin or CJK scripts. Languages using Arabic, Devanagari, Thai, or other writing systems are not represented. The dataset size per language is small (similar to FUNSD scale), limiting its usefulness for training language-specific models from scratch.

Access: Available on GitHub.

Table Detection and Extraction Datasets

10. PubTables-1M

What it is: A large-scale dataset for table detection, table structure recognition, and functional analysis, containing over 1 million annotated tables from scientific articles.

Who created it: Microsoft Research, derived from PubMed Central articles.

Why it matters: Table extraction is one of the hardest problems in document AI. Tables contain structured data that loses meaning when flattened to text, and accurately detecting table boundaries, rows, columns, and headers requires specialized training data. PubTables-1M provides this at a scale that no other public dataset matches.

The dataset includes annotations for table detection (locating tables on a page), table structure recognition (identifying rows, columns, and cells within a detected table), and functional analysis (distinguishing header rows from data rows). This three-level annotation supports training models that handle the complete table extraction pipeline.

Best for: Training table detection models. Building table structure recognition systems that preserve row-column relationships. Evaluating table extraction accuracy across different table complexity levels.

Limitations: All tables are from scientific articles, which tend to use simpler formatting conventions (clear borders, consistent headers, regular grid structure) compared to financial tables, government forms, or invoice line-item sections. Models trained on PubTables-1M may underperform on tables with merged cells, invisible borders, or nested multi-level headers common in business documents.

Access: Available on GitHub under a permissive license.

The Gap These Datasets Leave Open

These ten datasets cover the core document AI tasks: layout analysis, information extraction, classification, question answering, multilingual processing, and table extraction. Collectively, they have driven most of the progress in document understanding research since 2019.

But they share a common limitation: none of them adequately represent the financial, legal, medical, government, or insurance documents that production document AI systems actually process.

PubLayNet, DocBank, and PubTables-1M are exclusively academic papers. CORD and SROIE are exclusively receipts. RVL-CDIP is tobacco industry records from the 1990s. DocLayNet includes some financial and government content, but not at the volume or diversity needed for production fine-tuning. DocVQA and FUNSD use general business documents and forms, but the annotation schemes do not cover domain-specific extraction needs.

This means that any team building document AI for a specific business domain needs to supplement these public datasets with labeled data from their own documents. Public datasets provide the pre-training foundation and the evaluation benchmarks. Domain-specific labeled data provides the production accuracy.

How to Use Public Datasets Alongside Your Own Training Data

The most effective training strategy combines public datasets with custom labeled data in a staged pipeline.

Stage 1: Pre-train on large public datasets. Use PubLayNet or DocBank to give your model a general understanding of document structure. The large volume teaches the model what text blocks, headers, tables, and figures look like across many examples.

Stage 2: Fine-tune on diverse public datasets. Switch to DocLayNet to expose the model to layout diversity beyond academic papers. This stage teaches the model that documents come in many formats and that the patterns learned from scientific articles do not generalize automatically.

Stage 3: Fine-tune on your own labeled data. Use labeled examples of your specific document types (invoices from your vendors, contracts from your industry, forms from your organization) to adapt the model to your production documents. This is the stage where domain-specific accuracy is established.

The quality of the Stage 3 data determines the ceiling of your production accuracy. AI Asset Management's DocuGraph platform accelerates this stage by auto-labeling your documents with bounding boxes and element classifications in 15 to 30 seconds per document. The output follows PubLayNet and DocBank labeling conventions and exports as structured JSON, ensuring compatibility with models pre-trained on Stage 1 and Stage 2 datasets.

Stage 4: Evaluate on held-out production documents. Always evaluate on documents from your actual production pipeline, not on the public datasets your model was pre-trained on. The gap between public benchmark accuracy and production accuracy is where the value of domain-specific training data becomes clear.

Choosing the Right Dataset for Your Task

The right starting dataset depends on what you are building.

Building a layout detection model? Start with PubLayNet for pre-training, evaluate on DocLayNet for generalization. Understand the taxonomy differences between the two (PubLayNet's 5 labels vs. DocLayNet's 11) and decide which matches your application needs.

Building a form or receipt extraction system? Fine-tune on FUNSD (forms) or CORD (receipts) after pre-training on a layout dataset. Add your own annotated documents for the specific form or receipt types your system will process.

Building a document classifier? Start with RVL-CDIP for pre-training. If your classification categories differ from its 16 classes, create a small labeled set of your own document types and fine-tune.

Building a document QA system? Fine-tune on DocVQA. Connect the QA model to a RAG pipeline that retrieves relevant document sections before passing them to the QA model for answer generation.

Building a multilingual system? Pre-train with XFUND for cross-lingual transfer. Supplement with labeled documents in your target languages for the specific document types your system will handle.

Building a table extraction system? Start with PubTables-1M for table detection and structure recognition. Fine-tune on tables from your domain, since business tables differ significantly from scientific tables in structure and formatting.

Summary

The ten public datasets covered in this guide provide the foundation for building virtually any document AI system: layout analysis (PubLayNet, DocBank, DocLayNet), information extraction (FUNSD, CORD, SROIE), document classification (RVL-CDIP), visual question answering (DocVQA), multilingual processing (XFUND), and table extraction (PubTables-1M).

Each dataset has specific strengths, limitations, and intended use cases. No single dataset is sufficient for a production system. The most effective approach combines public datasets for pre-training and benchmarking with domain-specific labeled data for fine-tuning to your actual documents.

The quality and diversity of your training data remains the single largest determinant of document AI model performance. Public datasets give you the starting point. Your own labeled data gives you the production accuracy.
