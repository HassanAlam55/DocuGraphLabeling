How to Extract Tables from PDFs for Machine Learning

Tables carry most of the numerical value inside a PDF. Financial statements, invoices, research datasets, audit reports: the important information usually lives in rows and columns, not in the prose around them. But tables are also the single hardest element to extract cleanly, and getting them wrong will silently break any downstream machine learning model that depends on them.

Short answer: To extract tables from PDFs for machine learning, use a layout-aware Document AI tool that segments tables as first-class labeled elements, exports structured JSON with bounding boxes and confidence scores, and produces output directly compatible with PyTorch, TensorFlow, or Hugging Face. Rule-based parsers work for small, uniform corpora, but production ML pipelines almost always end up on a deep-learning-based approach.

This guide covers why table extraction is uniquely hard, the four methods that actually work in 2026, and a step-by-step workflow for turning PDF tables into training-ready datasets.

Key takeaways

  • Tables in PDFs have no native structure. What looks like a grid on screen is just positioned text or scanned pixels, so extraction has to reconstruct the row-and-column layout from scratch.
  • Traditional OCR flattens tables into unreliable text. For any ML pipeline, you need extraction that preserves cell boundaries, headers, and hierarchical relationships.
  • Four methods dominate today: rule-based parsers, OCR plus post-processing, deep learning table detection, and layout-aware Document AI platforms. Each has a distinct trade-off between accuracy, cost, and setup time.
  • Modern Document AI tools built on PubLayNet-style taxonomies extract tables at 90%+ accuracy in seconds, exporting JSON that plugs straight into PyTorch, TensorFlow, and Hugging Face.
  • Output format matters as much as extraction method. Bounding-box coordinates, cell-level labels, and confidence scores are what turn a raw extract into usable ML training data.

Why extracting tables from PDFs is uniquely hard

A PDF is a rendering format, not a data format. The file tells a viewer where to place characters and lines on a page, but it doesn't say "this is row 3 of a five-column table." That structure has to be inferred every single time.

Three things make it worse:

1. Tables have wildly inconsistent visual grammar. Some tables have ruled borders on every cell. Some have no borders at all, using whitespace alone to separate columns. Some span multiple pages with repeating headers. Some nest sub-tables inside cells. A parser tuned for one style typically fails on the next.

2. Scanned PDFs remove the underlying text entirely. A scanned document is just an image. There is no text stream to parse, only pixels to run OCR on, and OCR without layout awareness treats table content as ordinary text, destroying the grid.

3. Real-world tables carry semantic meaning that generic extraction misses. A "Total" row is not just numerically different from the rows above it; it plays a structural role. An invoice line item connects to a vendor at the top of the page and a tax figure at the bottom. Flat text extraction loses all of this.

For a machine learning pipeline, these failures are silent. A model trained on badly extracted invoice tables will happily learn the wrong patterns and generalize poorly, and you often won't see the problem until it hits production.

What "table extraction" really means for ML

For a machine learning use case, "extracting a table" is not the same as pulling out the visible text. A useful extraction produces at minimum:

  • Row and column structure preserved as a two-dimensional matrix, not a wall of text.
  • Header identification so column names can be mapped to features in your dataset.
  • Bounding box coordinates in a standard format like [x1, y1, x2, y2] so each cell is traceable back to its position on the original page.
  • Confidence scores per cell, so low-confidence extractions can be flagged for human review before they contaminate training data.
  • Hierarchical relationships where they exist, for example between a summary row and its detail rows, or between a table and the section header above it.

Any pipeline that stops at "text out of a PDF" is going to underdeliver for ML use cases. Anything less than the list above turns downstream work (data cleaning, schema mapping, feature engineering) into a manual grind.

Four methods for extracting tables from PDFs

There are broadly four families of approach in 2026, and most production pipelines mix at least two.

Method 1: Rule-based and heuristic parsers

Open-source libraries like Camelot, Tabula, and pdfplumber parse the PDF's internal structure directly, using rules to detect table boundaries from ruled lines or whitespace patterns.

Strong when: The PDF is text-native (not scanned), tables have clear borders, and the layout is consistent across documents.

Weak when: Tables are borderless, span multiple pages, sit next to other layout elements, or the source PDF is a scan. Accuracy on real-world enterprise documents typically ranges from 60% to 85% depending on how clean the layout is.

Best fit: Quick prototypes, small datasets, or documents you control end-to-end.

Method 2: OCR plus post-processing

For scanned PDFs, the first step is optical character recognition using an engine like Tesseract, followed by heuristic rules that try to reconstruct table structure from the OCR output.

Strong when: You have to work with scanned or image-based PDFs, and layouts are simple.

Weak when: OCR errors compound with structural reconstruction errors. A misread digit in an amount column is one problem. A misidentified column boundary shifts every value in the row, which is much worse.

Best fit: Legacy document archives where no better source exists.

Method 3: Deep learning table detection models

Modern approaches use trained neural networks to detect table regions and their cell structure directly from document images. Architectures include Table Transformers, TableNet, and detection-based models trained on datasets like PubTabNet, a public benchmark of more than 500,000 annotated tables from scientific papers, and PubTables-1M, a million-table benchmark released for training and evaluating table extraction models end-to-end.

Strong when: You need robust extraction across diverse layouts, including borderless and complex tables.

Weak when: You have to build, train, and maintain the model yourself. That includes labeling training data, tuning hyperparameters, evaluating against a benchmark, and updating the model as your document types evolve.

Best fit: Teams with dedicated ML infrastructure and enough document volume to justify the ongoing engineering cost.

Method 4: Layout-aware Document AI platforms

The fourth approach combines the strengths of the previous three. A pre-trained Document AI model handles layout detection, table region identification, and cell-level labeling in a single pass, then exports the result directly as structured JSON.

Platforms like AI Asset Management's auto-labeling tool fall into this category. Upload a PDF, and the model segments the page into logical regions (including tables), applies standardized labels drawn from the PubLayNet and DocBank taxonomies, and returns bounding-box-labeled output ready to feed into a machine learning framework.

Strong when: You need production-grade accuracy without spending months training your own model, and you want a consistent output schema across document types.

Weak when: You need extremely bespoke behavior no pre-trained model has seen (highly specialized scientific notation or non-standard chart-embedded tables, for example).

Best fit: Teams that want the accuracy of a deep learning approach without the overhead of building it in-house.

Step-by-step: extracting tables from PDFs for ML training

Here is a practical workflow that consistently produces training-ready table data at scale.

Step 1: Audit your source documents

Before choosing a method, look at a representative sample of your PDFs and answer three questions. Are they text-native or scanned? Are tables ruled or borderless? Do table structures repeat across documents, or vary widely?

The answers determine which method above is viable. Mixed corpora (some text-native, some scanned) almost always need a layout-aware Document AI approach.

Step 2: Extract tables into structured JSON

Feed each document through your chosen extraction method. The output should be JSON with, at minimum:

  • A pages array with page-level dimensions
  • An elements array of labeled regions per page
  • A bbox field in [x1, y1, x2, y2] format for each element
  • A label field marking table regions distinctly from text, section_header, and other zones
  • Optional confidence scores per element

This structure follows conventions used by public datasets like PubLayNet and DocBank, which means the output is directly compatible with pre-trained document understanding models like LayoutLMv3, Donut, and Pix2Struct.

Step 3: Review low-confidence extractions

Every serious extraction pipeline needs a human-in-the-loop step, even at 90%+ accuracy. Filter cells or regions below your confidence threshold, review them in a visual editor, and correct the labels before they enter your training set. Skipping this step is the most common way silent data quality issues get baked into a model.

Step 4: Export to your ML framework

Convert the reviewed JSON into whatever format your training pipeline expects: a PyTorch Dataset, a TensorFlow TFRecord, or a Hugging Face Dataset. Modern extraction platforms output JSON that maps to these formats without a custom preprocessing layer.

Step 5: Split, train, and validate

Standard ML hygiene applies once you have clean data: train/validation/test splits, benchmarking against a held-out set, and continuous monitoring in production. The point of investing effort in extraction is that these downstream steps can focus on model quality rather than data quality.

Real-world use cases: where table extraction earns its keep fastest

Table extraction pays for itself first in three document categories where the tables carry most of the informational value:

Financial statements. Balance sheets, income statements, cash flow statements, and 10-K filings are largely made of tables. Extracting them cleanly enables downstream ML models for forecasting, anomaly detection, and comparative analysis. A domain-trained financial labeling model can identify amounts, vendors, and transaction rows across statements and reports without a custom schema.

Invoices and receipts. Line-item tables are the reason invoice automation exists at all. Vendor, quantity, unit price, tax, and total need to be extracted per row, then linked to header-level metadata like invoice number and due date. An invoice-trained labeling model handles this end-to-end across any layout or template, from vendor invoices to purchase orders to credit notes.

Legal contracts with fee schedules and exhibits. Contracts often contain tabular exhibits: pricing tiers, payment schedules, deliverable lists. A legal-trained labeling model extracts these tables while preserving their link to the surrounding clauses.

Research papers. Scientific tables are dense with structured numerical data. PubTabNet alone contains half a million examples from research literature, which is why table extraction from papers has become a standard task in document AI benchmarks.

Common pitfalls at scale

Four things reliably go wrong when teams first move table extraction into production:

Extracting text without preserving structure. If your pipeline flattens tables into space-separated strings, you have thrown away the data you were trying to keep. Fix this at the extraction step, not downstream.

Ignoring confidence scores. Treating every extracted cell as equally reliable is how bad data enters training sets. Use the confidence field, filter aggressively, and route the rest to human review.

Custom label schemas that lock you in. If your extraction output uses proprietary label names, you can't use pre-trained models like LayoutLMv3 without a mapping layer. Stick to PubLayNet or DocBank conventions from the start.

No visual review step. A JSON file looks fine until you overlay the bounding boxes on the original PDF and realize half the columns are shifted by one cell. A visual editor is not a nice-to-have, it is the last line of defense before bad data reaches your model.
